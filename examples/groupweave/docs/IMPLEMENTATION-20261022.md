# 原生 Bot 第一批交付

本批对应 Linear AIL-15、AIL-28、AIL-98。主参照是 AstrBot 的完整 Bot 体验；
插件运行和配置复用 Koishi。OpenClaw 仅作产品类比，不引入其运行时。

## 本批完成条件

- `npm run start:koishi` 通过 Koishi Loader 读取普通 `koishi.yml`。
- 官方 Telegram adapter 是该入口唯一的消息消费者；旧预览入口单独保留。
- 官方 Help、Echo 不改上游源码即可加载；官方 SQLite 驱动保存生态插件数据。
- 群注册、配置查看、规则预览/确认、链接整理、取消复用现有 Store/actions。
- 默认配置、环境模板和容器启动方式可直接使用，不增加配置语言或导入器。
- 验证原生插件输出、业务正常链路和重启持久化；真实 TG 验收单独记证据。

## 已确认的边界

1. 保留现有平台管理员、群管理员、成员三层职责。Telegram 实时身份是群权限
   来源；Koishi authority 不替代群管理权。
2. GroupWeave SQLite 管应用群配置/任务；Koishi SQLite 管原生插件数据，使用
   不同文件，不同时打开已有独占数据库。不会因此声称任意插件已自动隔离。
3. 普通插件运行于应用进程；需要自由执行的 Harness 继续复用 Harness Bridge、
   既有 DSH 和 OpenShell Docker。本批不另造执行器、调度器或沙箱后端。
4. 默认配置只负责安装好的原生插件；群级参数适配、AI 私聊/群聊、媒体、RSS、
   定时等按既有功能清单后续交付。原生入口不会把旧入口的能力自动标成已迁移。
5. 先交付所有约定功能，再进行最终安全检查与反向案例；本批只做必要的功能验证。
6. 当前 Git 分支没有初始提交且含大量既有文件，增量修改现有功能分支；不重置、
   不清理、不整体暂存，不用空工作树替换现有工程。

## 顺序

1. 原生 Loader、锁定依赖、默认配置。
2. 原生业务命令与现有管理 API 同用一份 Store/actions。
3. 启停、配置、容器入口、功能验证与使用说明。
4. 将实证写回 Linear；未完成真实接入的 Issue 保持进行中。
5. 后续按 M1 AI → M2 媒体/定时/RSS → M3 群配置 → M4 任务/记忆 → M5 部署推进。

这里是功能交付记录，不增加另一套产品模型或运行协议。
