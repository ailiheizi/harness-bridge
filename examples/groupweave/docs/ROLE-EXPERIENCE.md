## 产品形态

GroupWeave 是一个给多个群使用的机器人，以及辅助管理和明确执行的面板。
成员的主要入口是 Telegram 对话；群管理员的主要任务是配置自己的群；
平台管理员的主要任务是维护可供各群选用的插件能力。

同一人可以在甲群为管理员、乙群为成员，也可以另外拥有平台维护资格。
这几种资格不能互相推导。界面呈现取决于当前作用域；服务端独立核验每次请求。
本地预览的身份选择器仅用于演示，不是正式环境中改变角色的功能。

| 角色与作用域 | 进入后先看到什么 | 可以做什么 | 使用资格来自哪里 |
| --- | --- | --- | --- |
| 平台管理员 | 插件目录、可用/启用状态、能力详情 | 开放或停用已接入能力；查看全局维护审计；执行受限维护 | 部署白名单，独立于群身份 |
| 当前群管理员 | 本群插件、配置与生效规则 | 从已开放能力中选择，调整允许参数，预览后启用；作为成员使用本群能力 | 当前 Telegram 群管理员查询 |
| 当前群成员 | 本群已开放功能、使用方式、可见结果 | 在群内用命令或明确 @ 调用；面板中提交本次输入并选择允许的结果范围 | 当前 Telegram 成员查询 |

三种角色复用同一个服务和相同业务检查。无需三套部署、每群一个 Docker、
每群常驻 Agent，或把全局控制台开放给所有群主。

## 平台管理员的旅程

1. 打开平台插件管理，查看每项已发布能力的名称、用途、真实绑定与状态。
2. 区分“已接入但关闭”“已接入并开放”“尚未接入”。尚未接入不能启用。
3. 查看能力边界：处理哪些输入、是否使用模型、是否发送到第三方、
   能否读取网络/文件/群历史、允许群管理员调整哪些字段。
4. 对已接入能力切换平台启用状态。群级配置保留，实际执行仍重新检查平台状态。
5. 新增或更新插件通过代码审查、依赖锁定、实际绑定、验证及应用发布完成。
   当前面板不在线下载、上传、更新或运行任意插件代码。
6. 数据维护和全局审计放在独立的次要入口，避免首页变成备份和运维操作集合。

平台视角回答“提供哪些能力、以什么边界提供”，不会自动获得各群成员资格、
群规则管理权、群任务原始输入或他人的私人结果。主机、发布代码和数据库运维
仍是可信边界，能够接触明文数据与备份；应用权限不构成对主机运维的保密。

插件详情显示随版本维护的真实信息，不构造第二套插件注册协议。
“随应用发布的能力”不能描述成已经具备插件市场、热安装或恶意代码沙箱。
版本和来源只能显示实际可核实的发布信息，不能给占位功能补造版本号或安装记录。

## 群管理员的旅程

1. 将机器人加入受控群，并赋予可靠核验当前群身份所需的管理员资格。
2. 在该群使用 `/register` 创建群空间。群与个人来自真实 Telegram update。
3. 打开自己有资格管理的群，看到本群插件启用情况、规则版本和成员使用方式。
4. 选择平台已开放的能力。配置页只提供该能力真实支持的参数。
   链接整理支持去重、排序、单次条数；欢迎支持普通文本模板；反广告支持
   本群阈值和词表。响应方式与输出语言属于本群设置。模型文件、解释器、
   凭据和工具集合不属于群管理员可编辑字段。
5. 用自然语言描述要求，或者在辅助表单精确调整。两种方式进入同一种提案。
6. 查看旧值、新值、影响范围、未知要求和不可用依赖。存在阻断项不能启用。
7. 确认启用时再次核验当前管理权并比较基准版本。其他管理员先修改后，
   旧预览必须重新生成，不能覆盖更新。
8. 用成员视角试用一次，核对实际结果，再把正确命令和触发方式告诉本群成员。

群管理员可先使用 `/settings` 查看本群生效参数，再使用 `/rules <群规则>`，
通过 InlineKeyboard 查看并确认。
按钮必须仍属于创建者、当前群、真实提案，并重新核验当前管理权。
管理员本人也通过普通任务入口使用插件，不获得“任意执行工具”的额外入口。

当前自然语言采用有限解析，不是 AI 任意理解。可识别 @/命令、语言、
链接整理、摘要、回显、链接说明、欢迎、反广告、群助手的有限开关，
以及去重、排序和条数；未知要求明确指出并阻断启用。欢迎模板和广告阈值/词表
使用现有辅助表单的字段校验与同一提案，不把自由文本当执行代码。
配置字段不能写入工具名、凭据、执行代码、Shell、文件路径或任意网络目标。

群配置中的“组合”是选择能力和允许参数。执行时 link-brief 使用已有固定
AI → 链接插件 → AI；群助手可以根据本次目标直接回答，或在本群链接能力
获准时选择同一 `organize_links` 工具一次。它不代表任意插件自动可调用、
任意条件工作流、任务依赖、DAG 或把 Skill 自动编译成代码。
群主提出新能力，平台维护并发布后再供各群选择。产品内的能力申请流程尚未实现。

## 群成员的旅程

1. 私聊 `/start` 可查看固定引导，不会列出或读取任何群，也不会以传入群 ID
   获取权限。当前私聊业务和私聊管理仍未接入；进入目标群后再操作。
2. 在群里发送 `/help` 或 `/plugins` 查看本群实际可用能力和正确用法。
3. 普通代码通过 `/links`、`/echo`、`/scan` 提交当前文本；也可明确回复一条
   本群文本后发命令。命令模式正常使用；mention 模式带实际 `@BotUsername`。
   纯链接明确 @ 保留零 LLM 路径；自然语言目标 @ 优先进入已开放群助手确认。
4. `/digest`、`/brief`、`/ask` 先解释第三方处理，再由本人点原生确认。
   每次只能授权当前选定文本；5 分钟签名绑定本人、本群、功能、源消息、
   原 update、输入和触发方式。别人的回复内容可以作输入，不能授予群权。
   伪造、跨群、换人、修改原文、过期和重复同意拒绝；最多保留 512 条已消费
   签名及过期时间，没有输入缓存，满额拒绝消费，重建 adapter 后旧按钮失效。
5. AI 任务有处理中反馈，可用 `/cancel` 或按钮取消本人在本群的活跃任务。
   摘要为 1 模型/0 工具；brief 为 2 模型/1 成功工具；助手允许 1/0 或 2/1。
   调用证据只说明流程完成，不保证回答事实准确；取消也不保证供应商停止计费。
6. 群内结果回复到明确输入消息并公开给当前群，保持话题；不声称只本人可见。
   欢迎由实际入群事件按本群普通文本模板生成，只一遍替换 `{name}`/`{group}`，
   显示名不执行命令/表达式；`/scan` 仅给判定建议，无删帖、禁言、封禁或训练。
7. 面板是辅助入口：选择有资格访问的群、使用已开放能力、提交本次输入，
   在提交前选择“仅自己”或“本群”。面板显式执行不受自动监听触发方式限制；
   面板选择“本群”仅在面板向同群成员共享结果，不自动向 Telegram 发消息。
8. 查看自己可见的结果与状态。私人结果只给创建者；公开结果给当前本群成员，
   但面板/历史里的原始输入仍只给创建者。公开结果可能包含输入内容，
   Telegram 已公开的命令与引用文本也没有私人假象，不提供自动语义脱敏。

成员界面应优先提供“使用功能”和“可见结果”，不会把禁用的规则编辑器
作为成员首页。成员可以了解当前规则及命令，但不能修改本群配置。
隐藏导航只是体验调整，服务端仍必须拒绝成员修改和跨群读取。

AI 默认关闭；应用专用凭据、平台开放、本群启用、每次确认分别检查。
当前没有自动群历史总结或群历史读取。欢迎已接入真实 Koishi 文本插件和
Telegram 事件，但仍须平台和本群启用；提醒仍缺外部调度绑定，保持不可用。
反广告缺批准模型、依赖或初始化成功证据时保持不可用/blocked，不把仅有
规则结果宣称为分类器成功；旧机器人验证、举报、申诉与自动处罚尚未接入。

Telegram 内面板还需要配置 HTTPS 和 Mini App，现有普通浏览器本地预览
不能证明成员能在 Telegram 内完成签名登录。不要把任意普通 URL 按钮说成
已经可用的 Telegram Mini App 入口；具体入口必须使用真实部署的 Bot/应用配置。

## 借鉴 Koishi 的部分

以下是官方机制事实与本项目的设计映射。设计映射是 GroupWeave 的选择，
不是声称 Koishi 已经原生提供本项目的多租户产品。

| Koishi 官方机制 | GroupWeave 的设计映射 | 当前实现边界 |
| --- | --- | --- |
| 控制台区分插件安装/依赖管理与插件启停/配置；停用保留配置 | 平台优先显示插件目录、状态与详情，群管理员配置已开放能力 | 无在线安装/依赖更新；代码随应用发布。参见 [安装和配置插件](https://koishi.chat/zh-CN/manual/usage/market) |
| 配置项显示必填缺失、修改未保存等状态 | 真实不可用原因、配置差异、阻断项和生效版本可见 | 本项目使用已核验配置字段与提案，不引入 Koishi Schema 或新的表单 DSL。参见 [安装和配置插件](https://koishi.chat/zh-CN/manual/usage/market) |
| 插件过滤器控制在哪些平台、用户、群或频道的会话中生效 | 给群管理员清楚展示“只影响当前群”和实际触发方式 | 当前只支持本群设置，没有任意 AND/OR 策略编辑器。参见 [过滤器](https://koishi.chat/zh-CN/guide/plugin/filter) |
| 指令和 help 提供成员使用入口，触发前缀降低群内误触 | 成员通过真实 `/help`、代码/AI 命令及明确 @ 使用 | 使用实际 grammY 命令与本群响应配置，不引入另一套指令运行时。参见 [指令系统](https://koishi.chat/zh-CN/manual/usage/command) |
| 多份配置受插件是否可重用及其配置能力限制 | 先检查每个外部适配器是否真的支持按群参数，再复用 | 不能假定每群创建一个插件实例即可；保留单服务与数据库中的每群配置。参见 [维护多份配置](https://koishi.chat/zh-CN/manual/recipe/multiple) |

Koishi 是成熟的跨平台机器人框架；官方仓库为
[koishijs/koishi](https://github.com/koishijs/koishi)。本轮参考其管理和成员交互机制，
已经引入原生 Context/Session/插件和生命周期，但未完整迁移官方 Telegram
adapter、Console 或 Market；没有复制外部插件运行图或添加插件市场。
GroupWeave 实际库与调用位置见 [REFERENCES.md](REFERENCES.md)。

## 不能拿界面机制替代的隔离

Koishi 插件分组用于组织配置，不等于 Telegram 群租户；会话过滤器决定消息
处理作用域，不会自动限制一个插件的 SQL、文件、网络或凭据访问。
这一限制是根据其官方过滤器语义作出的架构判断，不是官方多租户安全承诺。
见 [过滤器](https://koishi.chat/zh-CN/guide/plugin/filter)。

Koishi 默认用户 authority 是权限等级，高等级可执行低等级操作。这个全局
模型不能直接表达“甲群管理员在乙群只是成员”。GroupWeave 继续独立核验
平台白名单与当前群角色。见 [权限管理](https://koishi.chat/zh-CN/manual/usage/customize)。

平台是否开放能力、当前群是否启用、操作者是否为当前成员、实际对象是否归属
本群、输入字段能否读取、结果受众是否合法，都是执行前后必须落实的检查。
群规则、用户文本、Skill 和 AI 输出不能更改这些条件。

不可信 Node 插件即使体积很小，也可能读取共享进程或数据库。当前只加载
随版本发布的可信已审查代码；需要执行不可信代码时，先明确资源及副作用边界，
使用已有执行宿主或沙箱并另行验收，不能靠自然语言规则或 AI 审查声称完全隔离。

## 已有能力、缺口与验收

| 范围 | 已有代码基线 | 尚不能宣称完成 |
| --- | --- | --- |
| 平台 | 已接入能力全局启停、独立白名单、全局审计和受限维护 | 在线插件安装/更新/卸载、能力申请流、任意插件安全执行 |
| 群管理员 | 当前群角色检查、群配置、规则提案、版本比较、群内确认、`/settings` | 任意自然语言规则、每人永久私人 Agent 配置、任意功能链 |
| 群成员 | 本群任务/可见性、原生命令、回复/明确 @、AI 确认/反馈/取消、欢迎与面板 | 真实 TG 与 Mini App 验收、私聊业务/管理、自动群历史总结 |
| 执行 | Koishi 代码插件、默认关闭的摘要/混合/群助手、opt-in antiad 纯预测 | 真实供应商质量/用量、批准反广告模型分类效果与峰值、完整处罚和持续负载 |

界面验证至少覆盖三个身份、两个群：

1. 平台身份先看到插件维护；没有群权时不出现可编辑群。
2. 群管理员只看到自己有权访问的群；启用/参数修改经预览后生效。
3. 成员先看到实际可用的功能和正确命令；管理导航不误导为可编辑。
4. 成员和另一个群管理员的服务端越权请求仍被拒绝；平台身份不获得群数据。
5. 身份和群切换清理旧输入、私人结果、提案和异步状态；跨标签会话变化也清理。
6. 平台停用或本群移除能力后，成员不能运行，迟到成功也不能绕过交付复核。
7. 未接入能力、未注册群、缺少 Mini App 部署信息都显示真实原因。

上述验收需要分别记录离线权限测试、本地真实界面证据、真实 Telegram 外部
验收，不能以其中一种代替另外一种。后续迭代将新插件映射到同一角色契约，
避免再次把成员体验变成平台运维页的缩小版。


部署形态仍是同一个应用容器；欢迎、代码和助手不按群创建进程或常驻 Agent。
反广告用同一服务的 [opt-in Python 构建](../compose.antiad.yaml)，管理员批准的
只读模型和固定解释器不接受群用户/AI 选择，joblib/pickle 属于可执行代码信任
边界。旧生产数据库、模型、样本池和配置没有复制；私有源码复用范围见
[antiad 来源说明](../integrations/antiad/README.md)。完整模块与后续范围见
[MODULES](MODULES.md)，不以单容器限制代替峰值、效果或任意插件沙箱证明。
