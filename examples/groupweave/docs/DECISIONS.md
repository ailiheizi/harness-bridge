# 第一版实施决策

2026-10-11 增补决策 015–019；更早决策保留其当时范围，最新模块状态见
[MODULES](MODULES.md)。

日期：2026-10-07。用户已授权先实现一个可查看的整体应用，再按效果调整。下述是此次实现选择，不是未经验证的最终承诺。

## 001：外部应用，保持 Workflow-to-Skill 简单

actweave 保留 root 标准及两份 authoring Skills。机器人代码、可信身份、群配置、数据库和容器属于独立 GroupWeave 应用；业务执行复用 DSH 原生能力。其意义是用一个真实场景验证方法，不让 authoring 项目拥有执行器。

## 002：grammY + Fastify + React/Vite

借鉴 kmua 的群内机器人体验，复用 grammY 的 Bot API 和 middleware，使用 Fastify 提供普通应用 API。React/Vite 用于可实际操作的配置面板。没有复制 kmua 的内置 Agent，也没有同时加载 Koishi、NoneBot 和多套运行框架。

这比先打造通用插件平台更容易看到产品效果。平台现阶段只维护随应用发布的固定能力目录；群管理员组合已经验收的能力。库版本由 package-lock.json 固定。参考来源见 [REFERENCES.md](REFERENCES.md)。

## 003：先用原生代码任务证明零模型调用

首个示范功能为纯内存链接整理：没有外部副作用，不需要真实凭据，结果可以直接复核。它不代表任意群的全部业务需求；后续功能依照实际反馈选择。

采用 DSH 原生 `commands.execute`，固定 handler 调用 `tools.execute`，权限 guard 在实际执行前拒绝越界。没有自建 Shell runner、模型循环或工具执行协议。创建原生 Session / idle Agent 只用于命令和工具归属，不能等同于发起模型任务。

模型调用为零的主张只覆盖这一条实际路径。代码失败、拒绝和未知结果不转给 AI；AI 插件也不会因系统空闲而自动启用。

已读上游事实：DSH 的无模型命令不会创建 turn，而原生交互式审批要求 open turn。因此这一版只采用明确 allow / deny 的低风险固定工具，不伪造 turn 来绕过审批。

## 004：本地预览身份与真实身份分开

为让用户先看到完整产品，预置两个合成群、不同群管理员、群成员和平台管理员。服务端发放不透明 cookie，保存真实的演示成员关系；客户端不能传 role 扩权。

这是本机预览身份，不是 Telegram 认证。真实群必须从可信 Telegram update 获取群和操作者，核验当前管理权，显式接入租户与配置存储，之后再验收。无 Token 默认不启动 Bot；不能凭一份合成群配置向真实聊天发布结果。

## 005：规则先预览，启用必须比较版本

自然语言体验先由有限规则解析器完成，明显告诉用户支持的词义；不支持的要求进入 warnings，禁止启用。精确面板写入同一配置提案。

提案绑定创建者、群和基准配置版本。启用时重新鉴权并原子比较版本，防止多个管理员互相覆盖。请求结构采用严格允许字段，不允许群管理员注入命令、工具名、文件路径和私有凭据。

## 006：一个应用容器，按数据和请求隔离

不为每群创建 Docker。SQLite 使用群过滤、事务和服务端对象鉴权；任务有固定群、发起者、配置版本和结果受众。私人结果不因平台管理员角色而开放。选择本群分享只公开结果；原始输入是发起者专属字段，对其他同群成员返回明确隐藏状态。

同进程只运行平台维护、已审查的固定代码。将来需要文件、网络、凭据或不可信代码的能力，应分别选择已有沙箱/执行宿主并证明限制。此次设计没有宣称恶意插件也能得到完全隔离。

## 007：不因本地通过而部署服务器

先验证本机真实功能、拒绝路径和容器运行。deployment host 之前的只读基线只能帮助安排后续容量试验，不是性能保证或上线记录。本轮不改 deployment host，不读取现有密钥。

## 008：核心职责分离与有界执行

核心复审发现演示平台身份默认加入两群，混淆全局能力维护与租户管理。移除默认群关系，并将群 Role 限定为 admin / member；平台界面从群加载中独立。平台权限不推导群成员身份；若同一人另有群授权，仍须分别核验。

复审还证明部分迟到客户端响应可能回写到新身份；所有异步回写绑定当前作用域，身份变化清空原作用域，操作防重入且旧 finally 不能释放新操作。这是呈现隐私边界，服务端对象与字段检查继续独立执行。

DSH 两个 parallel 参数不是服务级任务上限。应用加入简单 fail-fast admission：总活跃默认 2、每群 1；超额 429，无队列。10 秒等待到期向原生命令/工具发送取消信号，但必须等待真实工具结束才释放容量和 scope；不合作代码只能占槽，不能宣称已硬停止。固定函数的末尾括号处理改为线性扫描，避免合规大小输入拖住共享事件循环。

数据库恢复假设同一库只有一个运行实例；使用 SQLite 现成独占锁落实该条件，第二实例不能改写第一实例的活跃任务。生产扩容/备份仍须重新选择与验收，不能靠多开进程绕过这个前提。

这些是外部应用的普通权限、生命周期和资源修复，不创造 Workflow-to-Skill 运行平台。当前范围与生产门槛见 [CORE.md](CORE.md)。

## 009：业务操作共用，成熟库负责入口机制

HTTP 和 TG 共用普通 actions 函数，避免两套解析、配置和执行漂移。grammY 负责
update、InlineKeyboard、API 与官方 ratelimiter；Fastify 官方 Cookie/rate-limit
负责基础 HTTP 机制；TMA.js author SDK 负责 Mini App 签名验证和原始 initData
获取；Zod 负责配置类型和范围校验。群对象、行、字段和受众仍是应用业务责任，
不会因为框架存在而自动成立。没有添加 Redis、独立队列或多平台 Bot 框架。

## 010：观察不能授权，投递未知不能重开

持久成员表只用于已注册群的观察与发现，每次真实操作仍查询 Telegram。平台 ID
只来自部署白名单，签名个人身份也不推出群权。迁群来自可信 service update，
原子迁移记录并固化旧 pending；旧 scope 不能迟到覆写。任务幂等键与 Telegram
投递 claim 各自持久化，发送失败/未知不自动重发，以明确损失可用性换取防重放。
这不是跨 Telegram/数据库的 exactly-once 保证。

## 011：使用原生 SQLite 维护，恢复明确时间点缺口

采用 Node SQLite 自带 backup，验证 schema、完整性与 hash；固定目录、无覆盖、
5份/256MiB限额，平台 API 不返回原始数据库。恢复只在停机运维 CLI 完成，先取得
同一个原生独占锁，在事务中复制快照，避免替换 inode 绕开活跃 owner。
旧快照缺少之后的 update/投递键，所以恢复必须隔离更新并人工确认时间点，
不能宣称任意旧备份能无损自动续跑。容量满拒绝新增，不删除重复保护重开执行。

## 012：一个显式、默认关闭的原生 AI 用例

智能摘要用 DSH 原生 SkillRegistry/Filesystem/ToolSkill/AgentLoop 和官方 Adapter，
固定审核目录，不引入自建加载器、循环或 provider router。固定模型、工具空集、
1 step/模型尝试、1024输出tokens、禁用重试；只有明确启用、专用凭据、平台开放、
本群配置与每次第三方处理确认均满足才发送本次文本。不读历史，不自动 fallback。
匿名ID和 dormant upload index 的路径显式设为本应用 DATA_DIR/dsh-ai，避免继承
宿主 HOME。原生完成只证明生成结束，不证明语义正确；用量未知保持 null。

## 013：借鉴 Koishi 管理体验，三种角色按职责进入

平台管理员首页改为插件列表与详情，显示实现、数据访问、入口、资源范围和全局
可用性；备份与审计位于独立维护入口。群管理员首页是本群管理，插件详情仅调整
本群允许参数，启停和参数修改仍经过原有提案与版本比较。成员首页只展示本群
已开放的功能、群内使用方法和可见结果，不呈现不可编辑的管理导航。

Telegram 的 /help 按当前角色解释入口，/plugins 只列当前群实际可用能力，
/settings 仅当前群管理员可以查看配置和调整说明。群内命令公开回复到当前群；
面板选择本群可见只共享面板结果，不自动发 Telegram 消息。

Koishi 的插件列表/配置/启停、成员指令帮助值得复用其设计。它的插件分组、
filter 与默认全局 authority 不构成我们需要的对象、行、字段与租户隔离，
不替代既有服务端检查。仍用当前 grammY/Fastify/DSH 与单容器，不引入第二套
Bot runtime、热加载或新权限 DSL。来源、使用旅程与尚未实现范围见
[ROLE-EXPERIENCE](ROLE-EXPERIENCE.md)。

## 014：Koishi 代码插件与 AI 组合（已选定，首个切片已引入）

用户进一步明确：先引入 Koishi 作为代码插件层，由既有 Harness 中的 AI/Skill
按目标编排、组合允许的能力；一个任务可部分 AI、部分代码。普通插件原生
执行，AI 工具使用插件实际命令/服务的明确绑定，不建立新流程引擎。
首个切片实现和验证以 [KOISHI-CODE-AI](KOISHI-CODE-AI.md) / ACCEPTANCE 为准。
以下保留选型时的依据；完整 TG adapter/Console 迁移仍未完成。

用户明确优先使用现有插件生态，仅借鉴界面不足以达到目标。推荐外部应用
直接采用 Koishi 核心、官方 adapter、原生插件和官方扩展机制；普通插件原生
执行，AI/Skill 才调用 DSH。优先依赖和自有插件，避免长期 fork 核心，也不
逐个把所有插件重新包装成 DSH 工具。

此方向修订 002 的宿主选择、003/009 的全部业务执行入口及 013 的仅设计借鉴；
上述条目保留此前依据。当前代码和本地容器已引入首个 Koishi 与 AI 混合切片，
完整接入迁移另行验收。三类资格、群配置审阅、CAS、自有
数据权限与投递证据保留。第三方插件的数据库、缓存、目标和生命周期逐项核验，
不能由 filter、Schema、全局 authority 或旧 112 项测试自动推出隔离。

平台使用全局插件/依赖管理；群管理员只配置平台允许的本群字段，不能获得全局
Console manager 权限。每群独立参数只采用插件实际支持的 reusable/computed
机制，未支持则保持平台参数或小补丁。Photon 是消息 SDK，当前不替代 Koishi
业务插件生态。完整一手来源、许可与限制见
[KOISHI-ECOSYSTEM-PHOTON](KOISHI-ECOSYSTEM-PHOTON.md)，先验证的闭环见
[KOISHI-MIGRATION](KOISHI-MIGRATION.md)。actweave 不增加任何运行平台。

## 015：先完成机器人群聊闭环，原生库负责模块

对比 Rose、AstrBot、kmua 后，优先补命令、私聊上手、当前功能发现、按钮、
进度、失败、结果和取消，而不是继续增加面板占位。grammY Composer 组织
已有单消费者的命令和事件，Koishi 原生插件实现链接和欢迎，官方 Echo 继续
直接使用未修改的 npm 包。没有第二个 TG polling，也不自建插件 manifest。

实际 TG 入口复用同一 actions/store。面板的私人结果与 TG 群内公开结果明确
区分；面板 group 分享不会冒充已经向 Telegram 发布。具体行为和证据见
[MODULES](MODULES.md)、[TELEGRAM](TELEGRAM.md)、[ACCEPTANCE](ACCEPTANCE.md)。

## 016：助手按目标选择获准代码，工具不授予身份

新增原生 `group-assistant` Skill，支持显式目标答复或一次链接整理代码调用。
仍使用 DSH 原生 AgentLoop，成功只接受 1 模型/0 工具或 2 模型/1 工具。模型
看不到群 ID、用户、发送目标、解释器和代码参数的可选择入口；宿主冻结任务
身份与配置，在实际工具调用时重查当前群授权，失败不转模型重试或切换供应商。

助手开放工具的选择来自 actions 的提交快照，不在后续异步阶段重新读取配置
扩大能力。每次输入分别确认第三方文本处理。原生签名按钮不存输入副本，
5 分钟过期、有界防重放，群配置不是持续访问群历史或自动付费处理的授权。

## 017：antiad 先复用判定接缝，模型与案件不能偷跨群

用户本地原项目已有纯 `Scorer`/`TextClassifier`；复制三个纯模块并保留源码
hash，比移植整套 aiogram 机器人、数据库和全局管理员更小。固定 Python
适配器只接 stdin 文本与规则，没有通用 Shell 或工具执行入口。当前 `/scan`
提供检测建议，不假装完整加入验证、举报、申诉和自动处置已实现。

每次群规则独立，只读基准模型由平台批准；旧共享训练样本/群反馈不自动导入。
`joblib`/pickle 是可执行内容，不接受群主或 AI 上传。缺解释器、依赖、批准
模型或真实探测时插件不可用，其余 Bot 能力可以继续运行。默认镜像 Node-only；
有需要才给同一个容器增加锁定 Python 依赖和模型只读挂载，不为每群起 Docker。
来源、接口、许可限制和剩余完整业务见 [antiad adapter](../integrations/antiad/README.md)。

## 018：撤权版本覆盖终态到投递的等待窗口

复审真实复现：任务结束后移除执行 controller，Telegram claimed 到 send 的
身份查询期间，插件 disable→enable 会导致只查 enabled 的旧结果恢复投递。
因此在现有 Group/Plugin/Task JSON 中保存服务端授权版本；平台可用性/启停与
各群功能启停递增对应版本，普通参数调整不递增。任务保存自身与代码依赖的
版本，claim 和实际发送前同步比较；缺旧版本的历史任务不自动重新投递。

这补的是应用鉴权，未新增状态协议或投递引擎。当前成员仍由 Telegram API
核验，版本不能代替成员资格。最后同步检查与调用 sendMessage 之间不再 await，
但 Telegram 已接受的远端数据不能因稍后撤权自动撤回，跨系统事务保证仍不存在。

## 019：复用触发与执行机制，通过普通组合形成能力（设计目标）

用户澄清“复用”指机制级组合，而非挑选几个成品功能或同时启用插件。推荐把
时间、事件、新消息入口接到同一有界业务执行路径；有限取数、条件判断、代码/
Agent执行、业务进度与结果输出由现有插件和 Harness 完成。提醒、日报、变化
监控与持续助手是这些机制的不同组合，不分别建设四套执行设施。

用户随后明确职责应拆为存储、接收端、Harness/代码与CLI调用入口。职责分开
仍可在一个应用容器运行：触发来源属于接收端，有限进度属于已有存储，执行
归现成Harness或代码插件；CLI是实际能力的调用入口，不另建执行运行时。
目前DSH/Koishi是SDK原生调用，不伪称通用shell CLI已接通；固定antiad worker
与停机maintenance是实际进程入口。真实群授权共用既有actions，在调用和
交付边界强制；运维CLI不开放给群配置或AI。

固定组合是普通代码函数/插件，Agent只选择已绑定且获准的能力；不用通用流程
图、配置 DSL、任意动态命令或无限模型循环来解决复用。机制仍在外部 GroupWeave，
actweave 不拥有定时器、队列、事件总线或状态服务。

同进程时间触发可评估 Croner；TG事件复用 grammY，AI会话继续使用真实 Harness
接口。timer库不负责持久化、租户鉴权、停机补跑或投递一致性；停止timer也不
代表已取消运行中的回调。具体依赖选型尚未安装、集成或验证。

计划创建/修改预览需呈现群与目标、输入来源、时间及时区、错过/重叠策略、
有效期和资源预算；每轮重核管理员及功能/计划授权版本。暂停、撤权与迁群
阻止旧结果，发送未知不自动重发。当前只实现即时任务与欢迎事件；完整定时/
持续组合及原生会话恢复仍为缺口，见 [MODULES](MODULES.md)。

## 020：规则预览可并行比较，确认使用版本检查且不重复报成功

2026-10-15 决定保留同一群、同一基础版本的多份待审候选。创建新预览不会
静默撤销另一份正在审阅的候选；管理员可以对照各条原生预览消息，明确选择
其中一份确认。先确认的一份通过版本比较并生效，其他基于旧群版本的候选
随后必须冲突，不能覆盖已经确认的规则。

已激活提案的旧确认按钮在 Telegram handler 拒绝，不重复发送“启用成功”。
Store/actions 的幂等返回不能直接视为一次新的用户操作成功。当前规则提案
没有按时间过期的 TTL，`createdAt` 与按数量保留不等于时间到期；不能把
“消息较旧”直接当失效理由。本人、本群、当前管理员、无未决警告和群版本
检查继续适用。AI 处理确认自身的五分钟有效期是另一项既有约束。

[本轮回归](../tests/telegram-acceptance-20261015.test.ts)覆盖两个 pending
候选、首次确认、旧版本拒绝和已激活按钮重放；真实 Telegram 证据以
[当日验收](ACCEPTANCE-20261015.md)为准，不由离线测试推断。

## 021：原生宿主单独交付，固定配置通过文件与镜像维护

2026-10-22 将 Koishi 完整宿主接入作为第一批功能实现。新增
`npm run start:koishi`，直接使用官方 Loader、Telegram adapter、Help、Echo 和
SQLite；不把第三方插件改造成旧 CodeBot 的固定文字命令。旧预览入口保留，

## 029：Docker Markdown 浏览器仅通过显式 user-namespace seccomp overlay 启用

2026-10-26 用真实生产镜像复现 ADR-027 的 Chromium 沙箱失败。Docker 默认
seccomp 下，`unshare -Ur` 返回 EPERM，Chromium 报 `No usable sandbox`。沿用
[Playwright 官方非 root user-namespace 配置](https://playwright.dev/docs/docker#crawling-and-scraping)：
固定 Moby 默认 seccomp profile（来源 revision
`moby/profiles@6fe7deb1b9fb7c0397a4593480d7d22b9ee8caef`），仅额外允许
`clone`、`setns`、`unshare`；不关闭浏览器沙箱。Docker 29.5.2 / Colima Linux
arm64 probe 在规则下 `unshare -Ur` 成功。

原生容器的 128 PID 上限才是后续挂起的根因。实际启动/渲染挂起时读取 cgroup v2：
`pids.current=84`、`pids.max=128`、`pids.events max=261`；内存约 216 MiB/512 MiB，
`memory.events` 中 high/max/OOM 均为 0。提升到 256 PID（内存仍为 512 MiB）后，
正式 `startKoishiHost()` 启动、健康检查返回 200、真实 `convertToImage()` 生成
800×800、11,183-byte PNG，进程正常退出。

保持 `cap-drop: ALL`，不添加 capability。固定 profile 沿用上述 Moby 默认规则，
额外允许 `clone`、`setns`、`unshare`；移除默认 `chroot` syscall 规则上的
`CAP_SYS_CHROOT` seccomp 条件。seccomp 只允许该 syscall，Linux 仍按进程所在
user namespace 的 capability 执行内核权限检查。实测非 root Chromium 在此配置
下保持沙箱并成功渲染。容器仍为只读根、no-new-privileges、512 MiB、256 PID、
1 CPU；未授予 SYS_ADMIN，未用 privileged/unconfined，也未传入 `--no-sandbox`。

profile 固定在 `deploy/seccomp/chromium-userns.json`，由 opt-in
`compose.koishi.render.yaml` 加入，并只将该可选部署的 PID 上限从 128 调到 256；
默认 Compose 保持关闭渲染及原限制。真实 Bot 的 Telegram `/mdimg` 收发和远程
目标 Docker 仍须单独验收。未增加渲染引擎、sidecar 或新的沙箱后端。


## 030：真实模型使用应用侧固定出站接缝与任务凭据

此前真实 Sub2API/OpenShell/DSH 链路已验证，但 Bot 要求的请求前额度和请求回执
没有部署实现。选择在 GroupWeave 可信应用中复用 Fastify/fetch，提供固定
`/v1/chat/completions` 接缝；目标、模型和真实密钥由受保护部署配置选择。
每任务生成独立短期凭据，绑定当前 task/tenant/actor 与原生 sandbox，再原子
准许一次真实上游请求。无重试、无动态目标、无额外模型工具；供应商未给 usage
时保留 null，不把请求次数当作金额账单。

受保护模块可按任务创建并释放原生 provider/profile。任务凭据由 OpenShell
已有凭据机制交给本任务沙箱；网络策略只开放本机计量路径，不能绕开额度直连
供应商。固定上游请求使用 HTTPS；沙箱到同宿主接缝复用 OpenShell 已验证的
host.openshell.internal 原生路径。请求计数来自实际出站，DSH session 来自
可信原生完成记录，二者绑定后才返回既有计量合同。

该接缝属于业务应用的凭据/计量责任，不加入公共 Harness Bridge，不新增通用
provider router、Agent loop、队列或第二沙箱后端。代价是每任务 provider 配置
有少量生命周期开销，先保障可用交付；不再把已经成功的真实模型调用写成未实现。

## ADR-033：提醒编辑复用上游创建/删除，不直接修改运行中的计划行

发送流程的本次提醒。当前同一接收器内短暂串行处理提醒修改；不是新增任务队列。

## ADR-039：复用上游验证，以代表性接入和本项目接缝作为交付依据

状态：采纳。日期：2026-10-29。来源：用户明确要求接通一个可用的 Koishi
代表路径后，不再把原生插件的所有功能逐项重测，并要求写入 ADR 和 AGENTS.md
以避免后续重新扩张测试范围。

### 为什么这样决策

本项目的价值是组合成熟的插件、Harness 和接收端。对同版本、未修改的上游代码
重新验证所有插件、参数、媒体格式和调用组合，会重复上游维护工作，消耗时间、
模型费用与服务器资源，并挤占尚未完成的功能交付。先前把“未逐项演示”持续列为
未完成任务，混淆了功能缺口与验证覆盖范围，造成验收不断增长。

### 决策

1. 直接复用的上游实现及其原生功能遵循锁定版本的上游契约。代表性的真实接入
   成功后，记录版本、部署环境、入口和实际结果，后续复用该证据；不再逐插件、
   逐子功能、逐参数组合重测上游。
2. 验证聚焦本项目接缝：安装和加载、消息与结果路径、身份/群/目标绑定、配置
   持久化，以及本次新改动的取消、清理或文件边界。通常一条能说明交付的正常
   路径足够；仅在本次改动涉及具体失败或数据风险时增加直接相关的反例。
3. 验证范围随实际改动确定。修改上游补丁、相关依赖版本、配置或运行环境，或
   出现真实故障，才重查受影响路径。已经通过且条件未变的其他功能不重复验证。
   文档及可逆低影响修改不因流程惯例新增测试；不自动增加组合矩阵、压力测试、
   长时间观察或独立验收平台。
4. “未逐项实测”单独说明覆盖边界，不自动生成 todo/issue，不单独阻塞功能票
   或里程碑。关闭功能票依据真实功能已接通及必要接缝证据，而非穷举完成率。
   真实未实现能力、已定位故障和明确未满足的需求仍须保留，不能靠改写验收掩盖。
5. 功能交付优先，完整安全检查按既定收尾阶段执行；本次改动自身必需的权限和
   数据边界不能删除。相关验证通过后继续交付，不无故扩大或重复检查。

### 代价与边界

接受未穷举上游行为及组合的覆盖范围，借助固定版本、上游维护和真实故障反馈处理
后续问题。代表接入成功不保证每个生态插件都兼容，也不证明完整多租户隔离。
故障可能来自本项目接线、配置、版本或上游，需按证据定位，不能预先全归上游。
用户未来明确要求的专项验收优先；扩大范围时记录具体触发原因和旧证据不足之处。

本决策约束后续测试工作，不追溯把未发生的测试写成通过。运行约束同步写入
项目根 `AGENTS.md`，实施和 Linear 只保留真实交付缺口。

## ADR-041：AI 文件出口固定于宿主个人会话与单一产物

复用上游已准备广播的本群RSS文本、原生schedule定时及原生数据库；不另抓网页、不做通用DAG。
每群有限计划先预览后由创建者确认，固定来源/模型/目标、期限和尝试上限；每次运行复核当前授权，
先保存当天尝试再启动模型，未知结果不自动重放。异步响应重核计划ID，旧计划不能停掉或污染新计划。

原因：补可直接使用的结果，保持数据、Harness与接收入口的既有分工。
代价：只提供按日汇总标题/链接，缓存有上限，不能表达任意流水线或保证全文完整。
详见 RSS-DIGEST.md；按ADR-039只检查新增接缝。

## ADR-046：广告复核入口诚实复用既有 AI，保留本地分类器缺口

日期：2026-10-31。原生入口并未接旧Python classifier，公开实现也缺私有模块。

先用已有assistant确认/授权/DSH/计量/取消提供显式 `/scan <文本>`，输入和结果标明AI复核、实际计费、
仅建议非处罚；固定包装不读取/写入对话、不开放代码工具。不复刻私有实现或引入未评估大权重。

这不交付原先本地零LLM分类器、群关键词/阈值评分或自动处罚等功能；它们继续明确列为缺口。
因此不得只凭新命令可用把AIL-118原本地能力范围全部关闭。详见 AI-AD-REVIEW.md。

## ADR-047：高频复核使用本地关键词，和 AI 复核分开

日期：2026-10-31。用户优先固定代码、现成能力与实际可用，不要求每次复核都运行模型。

原生宿主内置小型本群关键词匹配器，复用既有antiad功能位、群规则、任务与投递。
平台默认仍须开放，群配置单独启用。实现标记由可信宿主设置，不能由群/请求替换。
默认词表与显式空表在界面和预览分别表达；回滚恢复完整可信配置快照的缺省语义。

原因：公开快照缺私有训练分类器，不应为基础可用性引入未经许可的实现或大权重；
确定性规则无需模型或沙箱成本。`/keywords`明确是规则，`/scan`明确是付费AI。
代价：关键词会漏判/误判，不能替代原有分类器分数/阈值或完整自动群管；这些仍如实列缺口。
